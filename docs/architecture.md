# Instafuel – Architecture

Living document. Update the **Change log** at the bottom whenever models, constraints or endpoints change.

## 1. Overview

- One ASP.NET Core Web API project: `Instafuel.Api` (.NET 10).
- EF Core 10 + Npgsql talking to PostgreSQL. Postgres runs in Docker (`docker-compose.yml`).
- Serilog for logging (console + daily error file in `logs/`).
- No microservices, no service/repository layers yet. Controllers talk to `PgDbContext` directly. We'll add layers only when they're needed.

## 2. Folder layout

```
Instafuel.Api/
├── Controllers/   one controller per main resource, plain CRUD + a few actions
├── Dtos/          request records (what clients send), with validation attributes
├── Models/        EF Core entities + PgDbContext (Fluent API config lives here)
├── Migrations/    generated by `dotnet ef migrations add`, review before applying
└── Program.cs     DI, logging, Swagger, JSON options
```

## 3. Conventions

| Topic | Rule |
|---|---|
| IDs | `Guid` primary keys (except the old `Test` table). |
| Statuses | Lowercase strings (`"pending"`, `"in_transit"`). Allowed values are listed in a comment next to each property and checked with `[AllowedValues]` on requests. |
| Timestamps | Always `DateTime.UtcNow`. Dates without time (licence expiry etc.) use `DateOnly`. |
| Money / quantity | `decimal` with `[Precision]` on the model: money `(14,2)`, fuel quantity `(14,3)`, coordinates `(9,6)`. |
| Constraints | Unique indexes, max lengths, check constraints and delete rules go in `PgDbContext.OnModelCreating`, one block per entity. |
| Delete rules | `Restrict` for business records (orders, payments, deliveries, drivers, vehicles). `Cascade` only for child rows that mean nothing alone (order items, status history, inventory movements, supplier members). |
| Deleting | Soft delete (`IsActive = false` or a status) for anything other records point at. No hard deletes from the API. |
| Requests vs responses | Clients send `Dtos/*Request` records. Responses return the entity directly. `User.PasswordHash` is `[JsonIgnore]`. JSON uses `ReferenceHandler.IgnoreCycles`. |
| Errors | Each action has a try/catch that logs with `ILogger` and returns 500 with a short message (same pattern as `TestsController`). Validation → 400, missing → 404, duplicates/busy resources → 409. |

## 4. Entities by module

Logical design is in [database_schema.md](database_schema.md); this is what the code actually has.

| Module (plan.md) | Entities |
|---|---|
| Users | `User` |
| Suppliers | `Supplier`, `SupplierMember` (user ↔ supplier, composite key), `SupplierLocation` |
| Products & pricing | `Category` (self-referencing tree), `Product`, `SupplierOffer` (supplier's price for a product) |
| Inventory | `InventoryBalance` (one row per location + offer), `InventoryMovement` (audit trail) |
| Orders | `Order` → `SupplierOrder` (one per supplier) → `OrderItem` (price/name snapshot) |
| Payments | `Payment` (unique `IdempotencyKey`), `Refund` |
| Fleet & delivery | `Driver` (1-to-0..1 with `User`), `Vehicle` (company truck), `Delivery` (supplier order + driver + vehicle), `DeliveryStatusHistory` |

## 5. API endpoints

All under `/api`. Swagger UI at `/swagger` in Development.

| Resource | Endpoints |
|---|---|
| `users` | `GET`, `GET {id}`, `POST`, `PUT {id}`, `DELETE {id}` (deactivate) |
| `categories` | `GET`, `GET {id}`, `POST`, `PUT {id}`, `DELETE {id}` (deactivate) |
| `products` | `GET ?categoryId`, `GET {id}`, `POST`, `PUT {id}`, `DELETE {id}` (deactivate) |
| `suppliers` | `GET`, `GET {id}`, `POST`, `PUT {id}`, `PATCH {id}/status` |
| `orders` | `GET ?customerId`, `GET {id}`, `POST`, `PATCH {id}/status` |
| `payments` | `GET ?orderId`, `GET {id}`, `POST`, `PATCH {id}/status` |
| `drivers` | `GET ?available`, `GET {id}`, `POST`, `PUT {id}`, `PATCH {id}/availability` |
| `vehicles` | `GET ?available`, `GET {id}`, `POST`, `PUT {id}`, `PATCH {id}/status` |
| `deliveries` | `GET ?status`, `GET {id}`, `POST`, `POST {id}/assign`, `PATCH {id}/status` |

No endpoints yet for supplier locations/offers/members, inventory, or refunds.

## 6. Key flows

### Order creation (`POST /api/orders`)
1. Client sends customer, recipient/address and a list of `{ supplierOfferId, quantity }`.
2. Offers must be active, with an active supplier and product.
3. Items are grouped into one `SupplierOrder` per supplier, fulfilled by the supplier's first active location.
4. Name, unit and price are copied from the offer into `OrderItem`, and totals are calculated on the server.
5. Saved with one `SaveChanges`, which runs as a single transaction.

### Delivery status flow

```
pending ──assign──► assigned ──► dispatched ──► in_transit ──► delivered
   │                   │              │              │
   └──► cancelled ◄────┘              ├──► failed ◄──┘
                                      └──► cancelled
```

- `POST {id}/assign` (pending → assigned) checks the driver is verified, active, dangerous-goods certified, has an unexpired licence and is available, and the vehicle is active, has an unexpired fitness certificate and is available. Both are then marked unavailable.
- `PATCH {id}/status` follows the table in `DeliveriesController.AllowedTransitions`. `delivered` requires `DeliveredQuantity`, `failed` requires `FailureReason`.
- On `delivered`, `failed` or `cancelled`, the driver and vehicle become available again.
- Every change adds a `DeliveryStatusHistory` row.
- A supplier order can only have one open delivery. To retry after a failure, create a new delivery.

## 7. Not done yet (known gaps)

- Auth and role-based access (plan.md §2.9). Anyone can call any endpoint right now.
- 24h order lead time: `Order` has no requested delivery time field yet.
- Stock checks/reservation on order, inventory movements on delivery.
- Delivery fee, discount and tax rules (currently 0).
- Delivery status doesn't update `SupplierOrder`/`Order` status yet.
- Route planning, notifications, reporting.

## 9. Customer app (`instafuel_customer/`)

Flutter (Android + Web), Riverpod, go_router. Details in [instafuel_customer/README.md](../instafuel_customer/README.md).

- UI talks only to repository interfaces (`lib/data/repositories.dart`). They're backed by in-memory mocks for now. `lib/data/providers.dart` is the single place to switch to API implementations.
- Model/status names match the API (`OrderStatus`, `DeliveryStatus`, payment methods).
- **Orders are a list of lines, one per vehicle** (`vehicle + fuel + litres`). One order can fuel several vehicles, and the driver checks each vehicle's number plate separately.

### Backend gaps the app needs filled

| App feature | Needed in the API |
|---|---|
| Register / login | Auth endpoints, password hashing, tokens (JWT). |
| Customer vehicles + documents | `CustomerVehicle` table (see `database_schema.md`), document table + file storage, admin verification flow. |
| Multi-vehicle orders | Link `OrderItem` to a `CustomerVehicle` and snapshot its plate number. |
| 24h lead time | `Order.RequestedDeliveryAt` + validation (app checks it client-side already). |
| Plate check at delivery | Per-item "plate verified" flag/time set by the driver app. |
| Corporate accounts | Company, membership (pending/active, role), credit limit and usage. `corporate_credit` payment method. |
| Pricing preview | A quote endpoint (fuel subtotal + delivery fee rules). |
