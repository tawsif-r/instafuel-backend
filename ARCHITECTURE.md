# InstaFuel Backend Architecture

## 1. Overview

InstaFuel is a fuel delivery marketplace that connects customers with fuel suppliers and delivery agents.

The backend is built using ASP.NET Core Web API, .NET 10, Entity Framework Core, and PostgreSQL.

The application follows a Modular Monolith Architecture. This means the backend runs as a single application while its business responsibilities are organized into logical modules.

This approach simplifies development and deployment while allowing the codebase to grow in a structured way.

## 2. Technology Stack

| Component | Technology |
|---|---|
| Backend Framework | ASP.NET Core Web API |
| Runtime and SDK | .NET 10 |
| Programming Language | C# |

| ORM | Entity Framework Core |
| Database Provider | Npgsql |

| API Documentation | OpenAPI and Swagger |
| Local Database Environment | Docker Compose |

## 3. Architecture Style

In a Modular Monolith Architecture:

- The backend runs as a single application.
- Business responsibilities are separated into logical modules.
- Modules run within the same application process.
- Modules can share the same database.
- Internal business logic can be called directly without inter-service HTTP requests.
- Database schema changes are managed through Entity Framework Core migrations.
- The application can be deployed as one backend unit.

The current repository contains a single ASP.NET Core API project. The modules described in this document represent logical business boundaries; they are not necessarily separate physical projects or folders.

## 4. Logical Business Modules

### 4.1 Identity and Access Management

Responsible for managing users, authentication, authorization, and access control.

Responsibilities may include:

- Customer accounts
- Delivery-agent accounts
- Supplier membership and roles
- Authentication and authorization policies
- Role-based access control

### 4.2 Supplier Management

Responsible for managing supplier organizations and their operational locations.

Responsibilities may include:

- Supplier profiles
- Supplier members
- Supplier locations
- Supplier operational information
- Supplier access management

### 4.3 Product and Category Management

Responsible for organizing products available through the marketplace.

Responsibilities may include:

- Product categories
- Parent-child category relationships
- Product information
- Active and inactive categories
- Active and inactive products

### 4.4 Supplier Offers and Inventory Management

Responsible for supplier-specific product offers, pricing, and inventory tracking.

Responsibilities may include:

- Supplier product offers
- Product pricing
- Inventory balances at supplier locations
- Inventory movements
- Stock availability
- Inventory updates

### 4.5 Order Management

Responsible for customer orders and their fulfillment by suppliers.

Responsibilities may include:

- Customer order creation
- Supplier-specific orders
- Order items
- Order status management
- Supplier order fulfillment
- Coordination between orders and deliveries

### 4.6 Payment and Refund Management

Responsible for maintaining payment and refund records.

Responsibilities may include:

- Payment records
- Payment status tracking
- Refund records
- Payment-to-order relationships
- Refund tracking

Payment gateway integration and transaction processing must follow the project's payment requirements.

### 4.7 Delivery Management

Responsible for assigning and tracking deliveries.

Responsibilities may include:

- Delivery-agent assignment
- Delivery status tracking
- Pickup and delivery timestamps
- Delivery status history
- Delivery completion
- Delivery failure and cancellation tracking

These module descriptions represent logical responsibilities. Their final boundaries should be confirmed against implemented models, services, and business requirements.

## 6. HTTP Request Flow

A typical API request follows this flow:

    Client
      |
      | HTTP Request
      v
    ASP.NET Core Middleware Pipeline
      |
      | Request logging and configured middleware
      v
    Controller
      |
      | Request handling and application logic coordination
      v
    Business Logic
      |
      | Database operation when required
      v
    Entity Framework Core
      |
      | SQL through Npgsql
      v
    PostgreSQL Database
      |
      | Query result or persistence result
      v
    Entity Framework Core
      |
      v
    Business Logic
      |
      v
    Controller
      |
      | HTTP Response
      v
    Client

### 6.1 Request Processing Responsibilities

1. The client sends an HTTP request to an API endpoint.
2. The ASP.NET Core middleware pipeline processes the request.
3. Configured middleware can handle request logging and other cross-cutting concerns.
4. Routing directs the request to the appropriate controller action.
5. The controller coordinates request handling and application logic.
6. When database access is required, Entity Framework Core works with the PostgreSQL provider, Npgsql.
7. PostgreSQL executes the required database operation.
8. The result returns through the application layers.
9. The controller returns an HTTP response to the client.

The exact request flow depends on the endpoint. Authentication, authorization, validation, DTO mapping, and service classes should be documented in more detail as they are implemented.

## 7. Database Architecture

PostgreSQL is the primary relational database.

Entity Framework Core provides object-relational mapping between C# entity classes and database tables.

The Npgsql provider enables Entity Framework Core to communicate with PostgreSQL.

Database schema changes are tracked through EF Core migrations.

### 7.1 Start the Development Database

Run the following command from the repository root:

    docker compose up -d db

Check the database container status:

    docker compose ps

### 7.2 Apply Database Migrations

Run the following command from the repository root:

    dotnet ef database update --project Instafuel.Api

This applies the existing migrations to the database configured by the application.

### 7.3 Database Schema Documentation

For the documented entities and their relationships, see:

[Database Schema](docs/database_schema.md)

The documented schema should be verified against the actual EF Core models, configurations, and migrations before being treated as the definitive database structure.

## 8. Configuration and Secrets

The application uses a connection string named `PostgresConnection`.

The connection string must match the PostgreSQL database configuration used by the developer.

Development and production environments should use appropriate configuration for their respective databases.

Production credentials, passwords, API keys, access tokens, and other secrets must not be committed to source control.

Production deployments should supply sensitive configuration through environment variables or an appropriate secrets-management system.

## 9. Logging and Error Handling

The application uses Serilog for logging.

Logging should support:

- Diagnosing application failures
- Recording relevant operational events
- Capturing exceptions with useful diagnostic information
- Tracking incoming HTTP requests
- Supporting troubleshooting and monitoring

Logs must not expose passwords, access tokens, payment credentials, or other sensitive information.

Error responses should avoid exposing internal exception details to clients in production.

## 10. Deployment Overview

The high-level deployment architecture is:

    Customer / Supplier / Delivery Client
                     |
                     | HTTPS
                     v
             ASP.NET Core Web API
                     |
                     | Database Connection
                     v
                 PostgreSQL

The API and database are separate runtime components, even though the backend application follows a Modular Monolith Architecture.

### 10.1 Deployment Responsibilities

For production deployment:

- Host the API in a suitable application environment.
- Host PostgreSQL in a persistent database environment.
- Configure HTTPS and appropriate network access.
- Supply production configuration and secrets securely.
- Apply database migrations through a controlled deployment process.
- Configure application logging and monitoring.
- Establish database backup and recovery procedures.
- Avoid exposing the database directly to public internet traffic.
- Use appropriate access controls for application and database resources.

The actual production hosting provider and deployment topology should be finalized according to the project's infrastructure requirements.
